# Credential hygiene

What the compose files do about credential scope, and the steps only the operator can
take. Every step that touches the production host is **Class C**: follow
`docs/runbooks/deployment.md` (stop, wait 60 s, start; never `up -d`) and do it outside a
trading session. Findings about a particular host belong in a private note, not in this
repository.

## Scope of `.env` inside the stack

`env_file: .env` in the shared `x-hft-common` anchor hands every service that inherits it
the whole `.env`, whatever that service's own `environment:` list says.

```
  .env (broker identity + CA password + DB passwords + bot token)
     |
     +--> hft-engine    uses the broker identity                    (keeps it)
     +--> hft-bot       Telegram-facing, never talks to the broker  (now blanked)
     +--> hft-monitor   reads metrics and ClickHouse only           (now blanked)
     +--> wal-loader    reads WAL files, writes ClickHouse          (still inherits it)
```

`hft-bot` and `hft-monitor` neither import nor read the broker identity (only
`feed_adapter/shioaji`, `cli/_run`, `config/loader.has_credentials` and ops scripts do).
They now:

- override the six broker variables to empty (`environment` wins over `env_file`);
- mount `src`, `config`, `scripts` read-only. The engine bind-mounts the same `./src`,
  so a writable mount in a network-facing process was a way to plant code that runs in
  the engine at its next restart;
- drop every Linux capability (`cap_drop: [ALL]`). The bot also sets `no-new-privileges`;
  the monitor leaves that to `docker-compose.production.yml`, because compose
  concatenates list keys across `-f` files and rejects the duplicate item.

`docker-compose.prod.locked.yml` is regenerated by
`COMPOSE_PROJECT_NAME=hft_platform uv run python scripts/ops/generate_locked_compose.py`;
`tests/integration/test_prod_compose_parity.py` fails if it drifts from base + production.

Not changed here, deliberately: `wal-loader` (it inherits the shared environment list, and
narrowing it means converting that ~100-entry list to a mapping, a bigger diff for a process
with no network input) and the engine's own read-write `src` mount (the deploy procedure
copies into those directories; changing the engine's mount is its own Class C rollout).

## Operator steps

1. **Rotate shared secrets after any exposure of a CI secret or `.env` copy.** The database
   and Redis passwords exist under several names in `.env` (`CLICKHOUSE_PASSWORD`,
   `HFT_CLICKHOUSE_PASSWORD`, `MONITOR_CH_PASSWORD`; `REDIS_PASSWORD`,
   `MONITOR_REDIS_PASSWORD`, `HFT_MONITOR_REDIS_PASSWORD`) and must change together. Use 24+
   random characters, a different value per service. ClickHouse builds its `default` user
   from `CLICKHOUSE_PASSWORD` at container start, so it restarts first, then every client.
   Afterwards verify an unauthenticated login fails and an authenticated `SELECT 1` works
   per service. How the image's entrypoint treats a changed password on restart is NOT
   VERIFIED here; confirm with `SELECT name, auth_type FROM system.users`.
2. **Old `.env` copies.** Keep `.env*` at mode 600. Backups of superseded `.env` files hold
   superseded secrets; keep them off the host once the live `.env` is confirmed good.
3. **Old CI deploy key.** If the public half of the key that lived in the deleted
   `VM_SSH_PRIVATE_KEY` secret is still in `~/.ssh/authorized_keys`, remove it, but only
   after proving a login with a replacement key, and after checking it is not the key you
   use yourself (compare `ssh-keygen -lf` fingerprints).
4. **Dedicated ClickHouse users (needs a sim soak).** `config/clickhouse_init_users.sh`
   defines a least-privilege `hft_app` user but is mounted nowhere and only runs on an
   empty data directory. Its grants have never been exercised against the full workload
   (engine migrations, recorder, wal-loader, monitor, bot). Create the user by SQL on a
   running server, point one service at it in `HFT_MODE=sim`, and widen the grants only
   from the errors you see, before the engine uses it. Do not pass the password as a
   command-line argument.
5. **Session-lock file name.** The name falls back `SHIOAJI_ACCOUNT`, then
   `SHIOAJI_PERSON_ID`, then `SHIOAJI_API_KEY`. Set `SHIOAJI_ACCOUNT` to a non-secret label
   to avoid an identity in a file name, with the engine stopped: two processes that use
   different names do not exclude each other.

## Residual risk visible in the compose files

| risk | why it stays |
|---|---|
| engine mounts `src`, `config`, `scripts` read-write | see above |
| promtail mounts `docker.sock` | its `docker_sd_configs` need it; the fix is a read-only socket proxy, a new component |
| node-exporter listens on all interfaces (host network) | binding it to loopback would make it unreachable from Prometheus on the bridge network |
| ClickHouse, Redis, promtail run as root; no `read_only` rootfs in the base file | image-specific; each needs a tested change |
| monitoring images are old | CVE status not scanned; a Dependabot `docker-compose` entry (supply-chain change) proposes minor bumps |
